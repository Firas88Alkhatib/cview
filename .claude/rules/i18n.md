# i18n rules (@nuxtjs/i18n, D-20)

- No hard-coded user-facing text in templates or scripts. Use `$t('key')` in templates and `const { t } = useI18n()` in scripts.
- Add every new key to `i18n/locales/en.json` (camelCase segments), nested by area: `common.*`, `topbar.*`, `editor.<section>.*`,
  `preview.*`, `versions.*`, `validation.*`.
- Zod schemas stay language-agnostic (no `t()`, no text). Validation messages are translated globally by
  `app/plugins/zod-i18n.client.ts`, so `UForm` receives already-translated messages (D-37).
- Use interpolation and pluralisation (`t('versions.count', { n })`), never string concatenation.
- Format dates and numbers through i18n/`Intl`, never manually.
- PDF text is **not** UI i18n (D-23). It comes from `app/pdf/locales/<pdfLocale>.ts`. Never use `useI18n`
  inside `app/pdf/**`.
- `t()` is **not** type-safe (typed messages only give autocompletion). `tests/unit/i18n/keys.test.ts` scans
  `app/` for literal `t('…')`/`$t('…')` keys and fails on missing ones. Use **literal** keys so the scanner
  sees them. For dynamic keys, use an explicit map of literal keys.
- Tests: query by the English text from `en.json`. In **nuxt** tests, import it with `?raw` and `JSON.parse`,
  because the i18n plugin compiles a plain `.json` import into message ASTs. In unit tests, a plain import is fine.
